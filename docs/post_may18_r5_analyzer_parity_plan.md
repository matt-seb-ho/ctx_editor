## What's actually going on with "weaker analyzer"

Architecturally:

- **`ConversationAnalyzer`** in `src/ctx_editor/strategies/analyzer.py`
  is the main analyzer used by **Reset** (`context_edit_v2.py`) and
  **Augment** (`append_analysis.py`). It dispatches across a
  registry of prompt versions (`v4`, `v5`, `v6`, `v7`, `v8`,
  `v8_soft`, `v8_soft_cot`, `v8_single`, `v9`, `v11`, `s1`).
  Default is `v8` — the well-tuned, paper-grade two-query flow
  (Q1: user-messages-only → task spec; Q2: spec + full conversation
  → aligned + issues).
- **`AC3RewriteStrategy._run_analysis`** in `context_compaction.py`
  is a SEPARATE, hand-rolled analyzer step. It does not import
  `ConversationAnalyzer` (I grep-confirmed: zero references). It
  loads a single prompt file `compaction_analysis.txt` and runs
  one LLM call.

The `compaction_analysis.txt` prompt is not in the analyzer prompt
registry. It's a one-off prompt that was written when AC3-Rewrite
was added, with no review parity against the `v8` prompts that
Reset uses. Its quality is empirically worse: the
`sharded-GSM8K/2` smoking gun in the R4 resume doc (Reset's analyzer
correctly says *"the new value is 250% of the original purchase
price"*; the rewrite analyzer says *"interpreted as the selling
price being the total cost plus 150% of the total cost"*).

**Why this happened**: when AC3-Rewrite was implemented it was
treated as a separate strategy with its own pipeline rather than
reusing the existing analyzer infrastructure. This is the kind of
copy-paste-and-modify divergence that's easy to miss in code review
since both files independently work and produce structurally similar
outputs.

## Are the Reset/Augment analyses saved? — YES

There is a content-addressed `AnalysisCache` at
`outputs/analysis_cache/` that Reset/Augment/Gated-Reset all write to
and read from. Current state:

```
total cached analyses: 3,311
by analyzer model:     DeepSeek-V4-Flash 2257
                       gpt-5.4            531
                       Kimi-K2.6          523
by prompt version:     v8: 3311 (all of them)
```

These were generated by R1-R3 runs on the `htn50_52` prefix set.
Rewrite has been silently ignoring them because it uses its own
analyzer path. **So no — no missing data. The analyses are right
here on disk; Rewrite just hasn't been wired to use them.**

No need to pull from the other machine.

## Proposed R5 plan

### Phase 0: refactor `AC3RewriteStrategy` to use `ConversationAnalyzer` + cache

**One small, reversible code change.** In
`context_compaction.py`:

- Drop `_run_analysis` (or keep as a fallback) and instead
  instantiate `ConversationAnalyzer(prompt_version="v8",
  model=self.model)` in `__init__`.
- In `prepare_context`, call `self.analyzer.analyze(trace,
  model_client, cache=self._analysis_cache)` and consume the
  resulting `AnalysisResult` (which has `user_intent`, `aligned`,
  `issues` fields — same shape as the current dict the rewriter
  expects).
- Update the compaction-prompt template variable names to match
  (`user_intent` instead of `task_spec` if needed) so existing
  prompts still substitute correctly.
- Plumb in `AnalysisCache` the same way `context_edit_v2.py` does.

This means **every existing rewrite prompt (v1, v2, v3, v4, v5, v6)
gets a free upgrade to the `v8` analyzer** — and Rewrite hits the
3,311 already-cached analyses for free (so re-runs are basically
free).

### Phase 1: re-evaluate v1 / v3-no-conv with analyzer parity

Cheap. Just re-run the same prompts after the Phase-0 refactor.
Compare to Phase 1 numbers.

- **Hypothesis A**: v1 prompt with v8 analyzer materially beats
  Baseline (closes much of the gap to Reset just from analyzer
  parity).
- **Hypothesis B**: v3-no-conv with v8 analyzer outperforms v1 with
  v8 analyzer (the rewriter LLM benefits from cleaner input when
  the analyzer is correct).

Expected wall time: ~15 min per variant (12 cells, cache hits, MC=4).
Two variants ≈ 30 min total.

### Phase 2: unbiased GEPA round 2

**New `run_gepa.py` invocation with corrected framing.**

- **Seed**: v1 prompt (unchanged from R4 — fair starting point).
- **Reflection LM**: DeepSeek-V4-Flash (unchanged).
- **Budget**: 50 metric calls (up from 30 — more exploration).
- **Evaluator**: same mini-eval (12 problems on math conv0) for now;
  may broaden to cross-task subset in a follow-up.

**Crucially different**: the `objective` and `background` strings
will *not* prescribe the solution. Tentative drafts below — happy
to revise per your sign-off.

#### Proposed `objective` (unbiased)

> "Optimize the prompt template for the second LLM call of a
> two-stage context-editing pipeline. The first stage already
> produced an analysis of a multi-turn conversation. Your prompt
> tells the second LLM how to turn (some subset of) the available
> inputs into a single 'compacted context' message that will
> REPLACE the conversation history before a downstream assistant
> generates its next response on a fixed last user message.
>
> Maximize the downstream task accuracy (LiC math eval on
> DeepSeek-V4-Flash).
>
> Available inputs (use any subset; document what you keep and why
> in your prompt):
> - `{analysis_user_intent}` — analyzer's consolidated task spec
>   (strongly recommended).
> - `{analysis_aligned}` — analyzer's notes on what the assistant
>   got right (strongly recommended).
> - `{analysis_issues}` — analyzer's notes on what the assistant
>   got wrong (strongly recommended).
> - `{conversation}` — the full multi-turn conversation
>   (OPTIONAL — include if and only if it helps).
>
> Output format must include `<task_spec>...</task_spec>` and one
> of `<work_so_far>...</work_so_far>` or
> `<verified_work>...</verified_work>` XML tags (downstream parser
> requires this)."

#### Proposed `background` (minimal)

> "The compacted context is the only summary the downstream
> assistant sees of the conversation history (besides the unchanged
> system prompt and the last user message). The compacted message
> should give the assistant enough state to continue the task
> correctly, without dragging in distractions that might pull it off
> course. There is no single right answer for how to balance these —
> exploration is welcomed."

Notes on what I deliberately did **not** include:

- No reference to Reset's template.
- No reference to "faithful re-emitter" or "hallucination
  reduction" — that was the R4 framing bias.
- No editorial about which prompts have worked or failed.
- No "Reset gets 80%, current Rewrite gets 50%" anchor.
- No hint that "removing conversation" is a known-good move (your
  question — I'm telling GEPA `{conversation}` is optional, but
  not nudging it either way).

About the **(2) "removing distracting context pollution and
reorganizing previous work"** hint you raised: I'd lean toward
*not* including it as an explicit instruction. The minimal
background ("avoid distractions, keep state needed to continue
correctly") gets the same idea across without prescribing the
operations. If GEPA's first few rounds produce nothing interesting,
we can re-run with the extra hint as a controlled comparison.

#### Placeholder toggle

The proposed objective explicitly says `{conversation}` is
**optional**. This means GEPA can produce prompts that omit the
`{conversation}` placeholder entirely; the formatter (already using
`defaultdict(str, ...)`) handles missing placeholders gracefully.
So the toggle is a real search dimension this time.

If we want to make this even more explicit, I can add a brief note
that "prompts using a subset of inputs are valid — the evaluator
will substitute available placeholders only".

### Phase 3: validate the winner

Whatever Phase 2 produces (call it v7) gets a full LiC
DeepSeek-V4-Flash sweep (12 cells, ~10 min) and, if it beats v6,
a cross-model probe on gpt-5.4 + Kimi-K2.6 (~30 min).

### Phase 4 (stretch): GEPA on the analyzer prompt itself

Only do this if the Phase 1 result shows the **rewriter** is the
bottleneck (i.e. v1+v8 still has a large gap to Reset+v8). If most
of the gap closes from analyzer parity alone, then the rewriter is
not the priority and we don't need to GEPA-tune the analyzer.

## Risks / decisions for you

1. **Refactor compatibility**: changing `AC3RewriteStrategy` to use
   `ConversationAnalyzer` might shift dict-key names in the prompt
   templates (e.g., `task_spec` → `user_intent`). I'll handle this
   by keeping the prompt-side placeholder names as
   `{analysis_user_intent}` (alias) regardless of what the analyzer
   returns. Confirms backwards compat for prompts v1-v6.

2. **Cache key includes `prompt_version`**: switching to v8 means
   the cache hits are real (3,311 v8 entries exist) — no
   re-analysis cost on the htn50_52 prefix set.

3. **Should we tell GEPA about "remove pollution / reorganize for
   downstream use"**? My recommendation: omit. Let me know if you
   want it added.

4. **Same mini-eval subset (math conv0, 12 problems)** for GEPA, or
   broaden to cross-task? I'd default to same to keep the iteration
   tight, broaden only if results look math-specific.

5. **Reflection LM**: keep DeepSeek-V4-Flash for cost. We could try
   a stronger reflector (gpt-5.4) for ~$1-2 extra — open to it if
   you want.
