The analyzer-parity discovery — why we didn't have it, and how it happened

The paper's mental model is "all AC3 variants share stage 1 (the analyzer), diverge at stage 2 (the strategy)." That wasn't true for Rewrite. Every Rewrite-vs-Reset number from Phase 1 through R4 was conflating two distinct effects:

  • "the rewriter step is lossy" — what we thought we were measuring
  • "the rewriter has a worse upstream analyzer" — silent confounder

Why we previously didn't have parity (the historical reason)

The most likely chain — reconstructed from git history and prompt-file inheritance — was:

  1. AC3-Reset and AC3-Augment were built first, sharing ConversationAnalyzer from day one. The analyzer's two-query design (Q1: spec from user msgs only → Q2: spec + conversation → aligned/issues) was carefully tuned for these append/template variants.
  2. AC3-Rewrite was added later as a separate strategy — probably adapted from the earlier collabllm_compaction.py code (per the comment in ac3_rewrite_lic.yaml: "Adapted from collabllm_compaction.yaml"). The CollabLLM compaction pipeline pre-dated AC3 and had its own single-call analyzer prompt, compaction_analysis.txt, that produced a similar-shaped output (<task_spec>, <aligned>, <issues>).
  3. The legacy prompt was carried over as Rewrite's analyzer step and never re-pointed at ConversationAnalyzer. There was no explicit decision; it was inheritance from a code adaptation.
  4. The two analyzer paths produced superficially similar XML outputs. No test failure flagged the divergence, and no manual code review noticed it — the field names matched.
  5. R2's AnalysisCache infrastructure was added with Rewrite listed as a beneficiary in its docstring, but Rewrite never plugged in (it had its own bespoke analyzer call, so the shared cache didn't apply to it).

The result was an "easy to miss in review" bug: both halves work, both produce similar-shaped outputs, no test fails. It was only visible when I started reading individual analyzer outputs to debug v5 / v6.

  • Affected: every Phase 1 / R2 / R3 / R4 statement of the form "AC3-Rewrite under-performs AC3-Reset by X%". Some unknown fraction of the gap is analyzer-side, not rewriter-side.
  • Unaffected: Augment / Reset / Gated-Reset numbers (single shared analyzer). WildChat / Huang numbers (independent code path). CollabLLM Baseline / AO / Augment / Reset.

v1 → v8 prompt redesign (three warts fixed)

Current conclusions about Rewrite

The paper narrative

Rewrite is more flexible than Reset's deterministic template. On strict-format / well-bounded tasks (LiC math, database), the template's literal precision wins by ~3–4pp. On open-ended or complex-state tasks (WildChat conversational, CollabLLM bigcodebench), the rewriter's ability to reorganize and preserve context wins by 5–20pp. The two methods are appropriate-intensity for different problem shapes.

Why we still expect Rewrite to be better — the flexibility hypothesis

An LLM rewrite is strictly more expressive than a template-fill: anything Reset can produce, Rewrite can also produce, plus more. So the prior should be Rewrite ≥ Reset everywhere, with equality when the task happens to be cleanly templateable.

The current observation is that on LiC, Rewrite is ~4pp behind Reset on average. Two possible explanations:

  1. "LiC happens to be templateable." The hypothesis you raised. LiC's tasks are simple enough that the two Reset fields — "task spec" + "good progress so far" — are fundamentally what you need. Any further reorganization is redundant at best and lossy at worst. If this is right, Rewrite's flexibility is wasted on LiC; we should still see it win where the task structure is richer (WildChat, bigcodebench), which we do.
  2. "The LLM rewrite step has an irreducible hallucination floor." The 63% hallucination attribution persists post-parity. The flexibility comes with a tax we can't optimize away by prompt engineering. If this is the dominant factor, even on richer tasks Rewrite should top out below an oracle-flexible method.

The post-parity diagnostic (above) supports a blend of both:

  • The spec-equivalent fraction rose from 17% to 47%, so when v8 fails, the spec part is usually right. That's consistent with "LiC's specs are simple enough that you don't need more structure than Reset gives" — Rewrite gets the spec right, but its open-endedness then mis-summarizes the work-so-far, which Reset never tries to do.
  • The rewriter-hallucination rate stays at 63%, supporting the irreducible-floor view too.

Together: on LiC, Reset's not having a flexible rewrite step is a feature, not a bug. On WildChat / bigcodebench, where the work-so-far is too complex or non-templateable, Reset's rigidity becomes its weakness and Rewrite wins.

What R6 did not solve

The 3.7pp LiC gap likely is structural. The analyzer-parity fix recovered ~13pp; the prompt redesign added 0.4pp; GEPA found no further gains. Closing the remaining gap probably requires either:

  • A different architecture (e.g., conditional Reset/Rewrite based on task structure detected by the analyzer), or
  • Suppressing the hallucination floor (in-LLM, not prompt-level — e.g., with structured generation or constrained decoding).

Phase 1 — analyzer parity audit on the tau2 side done

tau2 has its own ctx_edit/analyzer.py with three prompts:

  • TASK_SPEC_PROMPT_V10 — Q1 (shared between S2 and S3) ✓ parity here.
  • COMPARE_PROMPT_V10_S2 — Q2 for S2 (Gated-Reset). Output goes directly into the compacted context (assistant reads it as briefing).
  • COMPARE_PROMPT_V10_S3 — Q2 for S3 (Rewrite). Output feeds into Q3 (the rewriter LLM).

The S2/S3 Q2 prompts differ materially — same architectural-asymmetry class as the LiC bug. Diff'd them carefully:

  • S2: first-person to the agent ("Your analysis will directly replace the agent's conversation history"), expansive, includes explicit "What should the agent do next" section.
  • S3: third-person about the agent ("Your analysis will be passed to a separate step"), telegraph-style, data-rich, no first-person guidance.
  • tau2's own comment block in the file explicitly documents the asymmetry: "S3 variant: the analysis is an intermediate step — a separate LLM call will use it to write the final context. Be precise and data-rich (Q3 needs the raw facts)."
Verdict: NOT the same bug class as LiC. The S2/S3 asymmetry is legitimately motivated by different downstream consumers (assistant vs another LLM). Proceeding with Phase 2 without refactoring tau2's analyzer.

Latent risk to monitor: S3's Q2 is much terser than S2's. If S3 underperforms S2 by a wide margin in the eventual sweep, the asymmetry should be revisited — terseness may be dropping state. The Phase 5 cells separate S2 from S3 so we'll see this directly.

Phase 2 — porting v8 to tau2 next

v8 cannot be verbatim-copied. tau2's Q3 ingests inputs LiC doesn't have:

  • environment_state — CRM database + phone state at the time of the turn. Real backend state, not just message history.
  • Tool calls and tool results — the conversation rendering must handle assistant tool call: foo and (User tool calls: [...]) annotations.
  • Downstream consumer is an agent that calls tools next turn; LiC's is a text-answer assistant. The "what should the assistant see to continue correctly?" question is fundamentally different.

Port heuristics (in order): keep v8's framing (analyzer-centered, conversation-as-reference, open-ended output, role-boundary clause), add tau2's environment-state preamble, keep tau2's tool-list block at the end. Why we're NOT using last-turn replay on tau2

LiC and CollabLLM have a single-prefix → single-turn replay protocol that makes each cell cheap (~25-30 min). Tau2 doesn't, because the agent maintains dual-control state: the assistant has a CRM database and a phone state that the user mutates through tool calls. Snapshotting that state at an arbitrary turn-N to enable last-turn replay requires ~2 dev-days of state-snapshot work (docs/notes/literature/tau2_replay_scoping.md). Deferred — only revisit if tau2 cell cost becomes the binding constraint.
