## 3. Oracle vs. upper bound (we beat them on database)

> ok, now that on database we beat the upper bound, we can't call them upper bound. maybe we use the word "oracle" somewhere? just removing all A is an oracle strategy for LiC but not for others.

**Disposition:** Apply.

**Action:** Globally retire "upper bound" in the AO/Concatenate-User framing. Use either:
- **"design-oracle baselines"** — signals that they are oracles *by the benchmark's construction*, which is exactly why database can beat them (schema-grounded consolidation is strictly more than reconstructing the original user query).
- Or, where space permits, **"construction ceiling"** / **"oracle reconstruction baselines."**

Then on the database row, we say "our method *exceeds even the design oracle*" which is a sharper framing than "beats upper bound."

**Reasoning:** Nebojsa's point is exactly right — calling something an "upper bound" we then exceed is self-contradicting. "Oracle" is the standard term in the RL / reasoning literature for "what a privileged strategy would achieve," so readers will parse it correctly.

**Disposition:** Apply.

**Action:** Rewrite the caption of Table 3 (tab:cognitive-hazard) to be explicit about the counterintuitive direction:
